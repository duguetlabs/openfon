# Realtime output admission and receipts

This correction addresses hosted security finding [3998401068](https://github.com/duguetlabs/openfon/pull/16#discussion_r3998401068) against `8bd42045`. Its preparation baseline is `ac80e7d63481dc6fa93d88fa8a34ce3436e6315a`.

## Admission

A single CallSession shares the following state across provider responses, item IDs, interrupted responses and upstream replacement:

| Bound | Policy |
| --- | --- |
| Decoded PCM per input message | Existing 480,000-byte limit retained |
| Audio byte allowance | 960,000-byte burst, refilled at 48,000 bytes per second |
| Audio/control event allowance | 400-event burst, refilled at 100 events per second |
| Identified response audio | 2,880,000 bytes (60 seconds of PCM24); bounded socket/response-ID correlation |
| Response metadata | At most 256 response entries across the call; IDs at most 128 characters; completed IDs cannot restart |
| Unconfirmed downstream output | At most 960,000 payload bytes and 128 binary/control writes |
| Receipt deadline | Oldest pending receipt must arrive within 10 seconds |
| Browser playback | At most 960,000 retained PCM-equivalent bytes and 400 AudioBuffer source nodes |
| Carrier output debt | At most 500 unconfirmed fixed media/control + mark pairs |

Base64 length gives a conservative decoded-byte upper bound before `atob` and PCM allocation. Empty audio still consumes event credit. The existing message JSON-size bound applies before JSON parsing. An admission failure gates the call and closes its upstream sockets synchronously, so later messages in the same JavaScript turn cannot continue parsing, decoding or forwarding. The existing single-flight finalizer then closes the caller and persists the terminal result. Failure text is locally fixed and does not include provider payloads, receipt IDs, URLs or credentials.

Provider `response_id` is correlated with its source socket; `response.done.response.id` closes only that identified response. Completed IDs remain bounded tombstones. A provider which omits response IDs has only a same-socket, segment-between-done 60-second bound: it is not a provable response boundary. Neither completion policy restores global byte/event credit or downstream receipt capacity.

These are safety limits, not measured optimal provider settings. Sustained output faster than real-time plus the 20-second burst, overlong monologues, excessive fragmentation, more than 256 response entries, or slow consumers fail closed. Normal multiple responses are not subject to a whole-call speech-byte cutoff.

## Downstream receipt protocol

Realtime `ready` advertises `audioReceipts: true`. Each binary frame is immediately followed by `{type: 'audio_receipt', id, bytes}`. Each flush/speaking control is followed by `{type: 'control_receipt', id}`. The ID is a fresh unpredictable UUID generated by the sender. The consumer validates and handles the preceding frame/control, then responds with `{type: 'audio_received', id}`. CallSession accepts only the exact oldest outstanding ID before its deadline. Guessed, repeated, expired and out-of-order IDs fail closed.

Negotiating receivers allow exactly one pending frame/control and its matching marker. Extra binary, a mismatched length, or an intervening flush cannot replace the pending pair. Old server connections which do not advertise receipts retain legacy framing, but still use bounded receiver playback. New servers require receipt-capable consumers; an old browser or custom bridge fails at the receipt window/deadline. Deploy matching browser and adapter code together.

A post-payload unpredictable marker proves the peer consumed the preceding ordered WebSocket payload. It is **not** a physical playback acknowledgement. Browser admission occurs before conversion/allocation; receipt does not release playback accounting. Actual AudioBuffer completion or explicit flush/discard releases local playback capacity, with late callbacks unable to subtract a later generation's buffers. A suspended AudioContext cannot accumulate unbounded nodes or retained audio.

The carrier adapters acknowledge internal CallSession output only after their existing bounded PCM conversion/playback admission. Carrier-side transport debt is separate from those internal receipts and from local playback queues. Every sent audio or flush pair registers a random carrier mark. Local flush does not return transport credit. A returned ordinary mark releases that entry; a returned post-clear/FLUSH_MEDIA mark is an ordered transport barrier and releases only entries preceding that barrier. Duplicate and late marks cannot release newer writes. The existing Telnyx mark and Asterisk MARK_MEDIA commands are reused. Missing carrier progress eventually fails closed; time and XON alone do not replenish transport credit.

## Runtime evidence and limits

The installed Workers `WebSocket` declaration provides `send(): void` and `readyState`, with no `bufferedAmount` or awaitable send/drain API. [Official workerd source](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/web-socket.c++) queues outgoing messages for its asynchronous pump. The optional bufferedAmount check is useful on other runtimes; it is not the Workers safety boundary. The receipt window supplies the bound when that property is absent.

Transport has already materialized an incoming frame before application admission; this does not limit network ingress allocation. The bounds apply per call/adapter, not as a distributed deployment quota. Control/transcript behavior outside this correction retains its existing limits. Receipt support and post-flush carrier barrier handling require synthetic runtime checks before release; no live carrier or live AI acceptance is established by source inspection.

The harness disposes all sockets, timers and Miniflare instances.

Initial failed candidate checks and original negatives are preserved in the owner fixture logs. These results do not establish physical playback, live AI/carrier acceptance, combined release correctness, or the required fresh security review.
