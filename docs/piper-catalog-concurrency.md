# Piper catalog concurrency bounds

[Official report5656369526](https://github.com/duguetlabs/openfon/pull/16#issuecomment-5656369526) identified concurrent misses on reviewed3d0da34507837e861a6e4ebc37b0382f31b6ccfe. The original32-entry LRU applies only after fetch and body parsing. It permits concurrent callers to independently fetch and buffer the same catalog.

## Admission and fallback

One scalar reservation per normalized endpoint is registered synchronously before I/O. At most32 unexpired reservations exist per isolate. A concurrent miss for an already-pending endpoint, or a new endpoint beyond capacity, immediately returns that caller's static fallback. There is no waiting queue or shared pending promise. Callers share only completed voice maps; each chooses its own language/fallback. Fresh cache hits remain available at full pending capacity. Completed maps retain their independent32-entry LRU and one-hour TTL.

Fetch, response, reader, abort signal and async continuations remain local to the initiating request/Durable Object context. Neither a follower nor admission cleanup awaits work owned by another context. This matters because Workers I/O objects are context-owned, and destroying an initiating context may prevent its finally continuation from running.

Reservations expire after1500ms, matching the unchanged native fetch abort deadline. A subsequent miss scans at most32 scalar entries and reclaims expired capacity, even if an initiating context never executes finally. A late result checks both its deadline and reservation identity before caching. Its finally releases capacity only if it still owns the reservation, so an older completion cannot overwrite data or delete a replacement reservation. Lease expiry is not permission to extend the originating fetch deadline. Native abort cancels live fetch/body I/O; abandoned-context cleanup relies only on scalar state.

Manual redirects,65536-byte body limit,64 voice entries, identifier validation, endpoint normalization and refusal to reuse expired/foreign maps remain unchanged. No CallSession, provider routing, audio, receipt or finalizer changes are included. This is a per-isolate bound, not a deployment-wide rate limit. Sustained sequential misses may still issue lookups; the correction bounds concurrent catalog work. During a cold/expired overlapping lookup, callers other than the admitted one may temporarily use a static voice instead of a catalog-specific voice. They do not wait for another call's I/O. Successful later calls use the completed map normally.

## Validation and proof limits

Against exact published source, all four original concurrency negatives failed as expected. The final admission contract also fails all four against original source. Final27 focused tests across existing/new catalog files pass, including immediate fallback, post-header body overlap,32-versus40 pending endpoints, expired refresh, cache/identity behavior, all failure/retry paths and abandoned reservation reclamation. Deliberately deferred mocks prove old results/finally cannot affect a replacement and expired owners cannot populate the cache. Those mock cases are not a claim that a native fetch ignores abort. Worker and web typechecks pass.

The synthetic actual-workerd probe uses the production catalog module at compatibility_date2026-05-01. Separate incoming requests and16 distinct Durable Objects demonstrate one owner/15 immediate fallbacks, then shared settled data. Both context modes also admit a follower after native headers while the body is observably pending, and it returns fallback before body completion. Native HTTP failure, body failure and1500ms abort each permit a fresh successful lookup. Runtime objects are disposed in finally. No external provider traffic is used.

The earlier pending-promise candidate passed25 focused tests/types and ordinary native sharing cases. It was replaced because those passes did not establish safety after initiating-DO destruction. The client-abort probe observed AbortError with a surviving follower, but this is only client-facing cancellation, not proof of context destruction. Initiating-DO cancellation/destruction is not exercised. The final design therefore removes the cross-context wait and reclaims expired scalar reservations without depending on a destroyed context's cleanup. The4s external watchdog is a harness ceiling; production1500ms was not widened.
