# gpt-realtime-2.1 and 2.1-mini: latency, and whether they still split utterances

> **Provenance.** The proposed-tier latency block and the matched detector control were
> recorded *after* the harness fix that moved marker generation from each arm to the paired
> cell, so treatment and control share a byte-identical system prompt. The four earlier
> blocks (`v21-ttfa`, `v21-split`, `vltier-split`, and the superseded `vltier-ttfa`)
> predate it. The tier block was rerun for exactly that reason and the effect grew — from
> −284 ms to **−357 ms** against the HD tier, with a tighter p90. Split rates are not
> affected by that confound: the marker lives in the system prompt, while splitting is the
> detector acting on byte-identical caller audio. The `v21` **latency** comparisons remain
> pre-fix and are marked where they appear.
>
> The recommendation table's **end-of-turn** row still carried the superseded block's
> figures (731 / 732 / 725) until each table was bound to the run it quotes; it now reads
> 733 / 731 / 717 from `vltier2-ttfa`. Nothing else moved, and no conclusion depended on
> it — every arm decides end-of-turn within ~16 ms of every other either way. It is worth
> stating because it is exactly the failure the binding exists to prevent, in the most-read
> table of the document, found by the checker on the day it stopped merging every dataset
> it could find.

## Recommendation: add one Kataleptic tier

**Voice Live serving `gpt-realtime-2.1-mini` with Azure multilingual semantic VAD.** It
beats the current HD tier on latency, matches it on turn-taking, and is a native
speech-to-speech brain instead of a cascade.

**Its cost advantage is not established.** Azure's Voice Live meters are named by service
tier, not by model, and which tier a `gpt-realtime-2.1-mini` bills at is not stated in the
price list. It is somewhere between **matching the HD tier at $0.020/min** (if Std) and
**~3.1× the HD tier at $0.062/min** (if Pro) — the latter still cheaper per minute than
nothing currently on offer with this brain's speed, but a paid upgrade rather than a free
one. [The cost section](#cost) gives both and names two ways to settle it. **Do not quote
a price match.**

Paired against the current HD tier it is **357 ms faster** (CI [−450, −271], p_adj 0.002,
survives correction). That comparison is *conservative*: the proposed arm runs direct to
Azure while the HD arm goes through the gateway, and from this vantage point the gateway
gets a ~31 ms shorter round trip, so the model-side advantage is if anything larger.

**And the advantage holds at the tail, which is the check that matters here.** The p90 of
the paired differences is **−183 ms** — still negative, so the proposed tier is faster than
the current HD tier even at the 90th percentile, not merely on a typical turn. Its own
distribution has no tail either: p50 1528 / p95 1853, IQR 144 — the tightest of any arm
across either report — and end-of-turn 733 / 748 ms. That is the opposite of what OpenAI's semantic detector does, and it is why
this tier is the answer rather than a detector flag on the tiers that already exist.

**The reason this tier exists at all is the detector.** Azure's multilingual semantic VAD
is the only one that eliminates clause-pause splitting *without* costing latency — against
a matched control on the same brain and stack its end-of-turn is **+0 ms, CI [−6, +21]** —
and it is reachable only through Voice Live. OpenAI's semantic VAD costs 454 ms and a 4.5 s p90, and on the mini brain it does
not even work (4/12 splits remain). Azure's takes the same brain to **0/12**:

### Two things "strict upgrade" would flatten

**Deflection carries to the proposed tier, and equal groundedness does not retire it.**
Counting replies where the agent says it cannot see or access the schedule:

| arm | deflecting |
|---|---:|
| `vl21mini-azsem` (proposed) | **2/20 — 10.0%** |
| `vl21-azsem` (proposed) | 2/20 — 10.0% |
| `vlnat-azsemantic` (gpt-realtime-2 on the tier) | 2/19 — 10.5% |
| `gw-hd-server` (current HD) | **1/40 — 2.5%** |

Every native brain on the Voice Live stack deflects at ~10%; the cascade the HD tier runs
deflects at 2.5%. It is not a 2.1 trait and not a detector artefact — it tracks the
*brain type*.

This matters because **a groundedness score is structurally blind to it.** "I can't see our
live schedule" invents nothing, so it should score *well* on groundedness while being
useless to the caller. Two brains scoring an identical 0.741 is therefore not evidence that
they behave equivalently on a call — it may be the metric that cannot see the difference,
in exactly the way a median could not see the semantic-VAD tail. The check that would
settle it is whether the quality run's own transcripts show the same ~4× gap; that is a
re-read of data already collected, not a new run.

**The voice catalogue changes.** The HD tier offers 600+ Azure neural voices, and OpenFon
actively manages them — `call-session.ts` sets `voiceManaged` on HD and hot-swaps the voice
when it detects the caller changing language. A native tier exposes **10 OpenAI voices**,
picks its own, and that machinery switches off. For a business that configured a specific
voice, or a multilingual line relying on per-language voice-following, this is a behaviour
change rather than an upgrade. Prosody is better; selection and language-following are not.

### One reason not to ship it yet

**Every native brain deflects at ~10%, against the HD cascade's 2.5%** — see
[the deflection table above](#two-things-strict-upgrade-would-flatten) and
[the observation below](#an-observation-not-a-result-the-mini-tier-deflects). It is not
specific to the mini tier and not specific to 2.1: `vl21mini-azsem`, `vl21-azsem` and
`vlnat-azsemantic` all land at 10.0–10.5%, and the gateway-side native arms at 7.9–30%,
while `gw-hd-server` sits at 2.5%. It tracks **brain type**, so the proposed tier inherits
it whichever model id it carries.

That is a crude regex over a few dozen replies and confounded by which text each arm saw,
so it is a hypothesis rather than a result — but it is the one thing that could disqualify
the tier, and it is what the quality benchmark (task #14) should settle. **Do not adopt on
latency and price evidence alone.**

If the deflection turns out to be real, the same tier with **`gpt-realtime-2.1`** instead of
the mini is the fallback: **2026 ms p50**, 0/12 splits, and no detectable difference against
the current `gpt-realtime-2` tier (−155 ms, CI [−391, −20], p_adj 1.00) — so it buys clean
turn-taking and a newer brain without a latency penalty, just not the mini's speed. On the
proposed tier it is also **260 ms faster than gpt-realtime-2** on the same stack
(p_adj 0.020, survives).

## Answer

**1. gpt-realtime-2.1 is faster than gpt-realtime-2, and 2.1-mini is faster than anything
else we have — by a lot.**

| tier (server VAD) | TTFA p50 | p90 | IQR | vs gpt-realtime-2 |
|---|---:|---:|---:|---:|
| `gpt-realtime-2` | 2507 ms | 2808 | 420 | — |
| Voice Live gpt-4.1-mini (HD tier) | 2125 ms | 2439 | 673 | −382 |
| **`gpt-realtime-2.1`** | **2061 ms** | 2349 | 311 | **−352 ms** (p_adj 0.002) |
| **`gpt-realtime-2.1-mini`** | **1404 ms** | 1590 | **181** | **−1022 ms** (p_adj < 0.001) |

`gpt-realtime-2.1-mini` is **579 ms faster than the HD tier** (p_adj < 0.001), which was
the fastest thing available before today, and has the tightest spread of any arm ever
measured here. `gpt-realtime-2.1` matches the HD tier (+17 ms, null) while being a native
speech-to-speech brain.

**2. Both 2.1 tiers still split utterances under server VAD — 12/12, exactly like
gpt-realtime-2. Do not assume the newer brain fixed it; it did not. And OpenAI's semantic
VAD is not the remedy: it carries a 4.4 s end-of-turn p90 on 2.1, so it swaps a silent
defect for multi-second dead air on one turn in five.**

**But semantic VAD is not the same answer for both tiers:**

| tier | server VAD | OpenAI semantic VAD | what OpenAI semantic VAD costs |
|---|---:|---:|---|
| `gpt-realtime-2.1` | 12/12 split | **0/12** | median +106 ms, **p90 +3490 ms** |
| `gpt-realtime-2.1-mini` | 12/12 split | **4/12** | median +734 ms, **p90 +3779 ms** |

> **Read the p90 column, not the median.** The cost of OpenAI's semantic detector is
> *bimodal* — and here that word is earned by looking at the differences themselves, not
> inferred from two quantiles: four turns in five cost ~100 ms, and four of twenty cost
> over a second, three of them clustered near **three and a half seconds**, with clear
> separation between the groups. A median describes the common case and says nothing about the case
> that matters on a phone call. An earlier draft of this document summarised it as
> "+106 ms (null)" — that line was wrong, and it is the correction that matters most here.

### Recommended defaults

* **`gpt-realtime-2.1` → do NOT use OpenAI `semantic_vad`.** It does eliminate splitting,
  but it replaces a reproducible silent re-segmentation with a 1-in-5 chance of a
  ~3.5-second silence. On a phone call that is a worse failure, not a better one.
* **`gpt-realtime-2.1-mini` → same, and it does not even fix the splitting** (4/12 remain).
* **Until the Voice-Live-served tier exists, `server_vad` is the lesser evil on both 2.1
  tiers.** Silent splitting is a real defect, but it is inaudible and costs no time; a
  multi-second dead air is neither.
* **The actual fix is [the proposed tier](#recommendation-add-one-kataleptic-tier).**
  Azure's semantic detector reaches 0/12 with **no tail at all** — end-of-turn p50 733 ms,
  p90 748 ms, IQR 14 ms.

There is also a delivery problem that affects any default you set: see
[the gateway drops the setting intermittently](#the-gateway-drops-the-setting-about-1-time-in-8).

**The p10/p90 pair is why the two semantic rows are not "no detectable difference".** For
`gw-21-semantic` − `gw-21-server` the differences run median +106, p75 +558, **p90 +3490**,
max +3864 — while the *best* case saves only 457 ms. It was slower on **13 of 20 turns and
faster on 7**, so this is not "almost never faster": it is a **magnitude** asymmetry, losses
an order of magnitude larger than gains, and a caller notices four seconds of silence but
never notices 300 ms. The sign test asks whether the differences are mostly positive, which
they barely are; it is silent about how much each one costs. This is the third time in this project a
median has hidden a tail, so the paired table now carries p90 for every comparison.

### The semantic-VAD tail is the detector, not the model

The marginal table above already shows it — `gw-21-semantic` p90 **5465 ms** against
`gw-21-server`'s 2349 — and the decomposition says where it comes from:

<!-- data: v21-ttfa -->
| arm | detector | end-of-turn p50 | end-of-turn **p90** | engine-only p50 | engine-only p90 |
|---|---|---:|---:|---:|---:|
| `gw-21-server` | server | 738 | **805** | 1322 | 1556 |
| `gw-21-semantic` | OpenAI semantic | 1180 | **4442** | 976 | 1419 |

**Engine-only is *lower* on the semantic arm at every percentile** — the model generates
sooner, because it is answering a whole sentence rather than a fragment. The entire tail
is the detector: up to 4.5 seconds spent deciding the caller has stopped talking. That is
the same behaviour measured on gpt-realtime-2 in the merged report; 2.1 did not change it.

### The gain is in the model, not the detector

Splitting TTFA into the detector's end-of-turn decision and everything downstream:

<!-- data: v21-ttfa -->
| arm | `speech_stopped_ms` p50 | engine-only p50 |
|---|---:|---:|
| `gw-2-server` | 739 | 1760 |
| `gw-21-server` | 738 | **1322** |
| `gw-21mini-server` | 744 | **657** |
| `gw-hd-server` | 737 | 1370 |

Every server-VAD arm decides end-of-turn within 7 ms of every other — the detector is not
where anything differs, exactly as in the merged report. The whole improvement is
inference plus synthesis: **gpt-realtime-2.1-mini produces its first audio byte in 657 ms
of model time, less than half the HD tier's 1370 ms**, and that difference survives
correction (−595 ms, p_adj < 0.001).

## Question 2 — does 2.1 still split?

`de-short` contains a clause pause after "Guten Tag," longer than
`silence_duration_ms = 550`. Server VAD commits early, starts a response, and cancels it
when the caller resumes.

<!-- data: v21-split -->
| arm | brain | detector | turns split |
|---|---|---|---:|
| `gw-2-server` | gpt-realtime-2 | server | **12/12** |

**The newer brains inherit the behaviour exactly** — 12/12 on both, identical to
gpt-realtime-2, with zero discordant cells against it. As in the merged report, every

nothing; the model answers a sentence fragment.

### Semantic VAD does not fully fix the mini tier

`gw-21mini-semantic` still split on 4 of 12 turns. This is not the configuration race —
all 12 turns have `config_verified = true` with `semantic_vad` echoed back, and no turn in
the run was rejected. The 4 split turns show the fragment transcript
(`'Haben Sie am Donnerstagnachmittag noch einen Termin frei?'`); the 8 clean ones show the
full sentence.

So on the mini tier, semantic VAD is a **mitigation, not a fix**, and an expensive one:
+734 ms at the median and a p90 of 5123 ms. Its `speech_stopped_ms` p90 is 4506 ms — the
same multi-second end-of-turn tail that made OpenAI's semantic VAD unusable on
gpt-realtime-2 in the merged report.

### The detector costs nothing on this stack — with a matched control

An earlier draft supported this by comparing `vl21mini-azsem` against `gw-hd-server` on
end-of-turn. That comparison varies **brain, serving path and detector at
once** and cannot attribute anything to the detector. It has been replaced with the
control that can: `vl21mini-server` — *same brain, same Voice Live stack, server VAD* —
so only the detector differs. (Voice Live does accept `server_vad` on a gpt-realtime brain
end to end; the control is possible.)

<!-- data: ctrl-ttfa -->
| comparison (brain + stack held constant) | pairs | median Δ | 95% CI | p90 Δ | p Holm | verdict |
|---|---:|---:|---|---:|---:|---|
| end-of-turn, `vl21mini-azsem` − `vl21mini-server` | 20 | **+0 ms** | **[−6, +21]** | +29 | 1.000 | **equivalent within ±50 ms** |

That is a genuine equivalence claim under this report's own interval rule — the whole
confidence interval sits inside ±50 ms — not a null read off a point estimate. Marginals:
732 ms p50 / 744 p90 for Azure semantic against 719 / 743 for server VAD.

inferred.** Compare OpenAI's on the same brains: 1189–1330 ms p50 with a 4.5 s p90.

| comparison (brain + stack held constant) | cells | treatment splits | control splits | McNemar p |
|---|---:|---:|---:|---:|
| `vl21mini-azsem` vs `vl21mini-server` | 12 | 0/12 | 12/12 | 0.00049 |

The server-VAD arm is answering a sentence *fragment* and the semantic arm a whole
sentence. Less to answer is faster. End-of-turn is the metric where the two arms are doing
comparable work, which is why the claim rests on it.

## The gateway drops the setting about 1 time in 8

Asking for `semantic_vad` through the gateway and reading back the echoed session, 8
sessions per tier:

| tier | echoed `semantic_vad` | echoed `server_vad` |
|---|---:|---:|
| `gpt-realtime-2.1` | 7/8 | **1/8** |
| `gpt-realtime-2.1-mini` | 8/8 | 0/8 |
| `gpt-realtime-2` | 8/8 | 0/8 |

This is the same session-update injection race documented in the merged report for the STT
model and turn detection: the gateway dials its upstream lazily and its own injected
`session.update` sometimes lands after the client's. The harness rejects those turns as a
control divergence, which is why the benchmark numbers are clean.

**Production has no such check.** Setting `semantic_vad` as the default will therefore
intermittently fail to take effect, silently leaving `server_vad` — and therefore
splitting — on roughly one session in eight. Two options, not mutually exclusive: assert
the echoed `turn_detection.type` in `call-session.ts` and reconnect on mismatch, or ask
Kataleptic to apply its injected defaults before accepting the client socket rather than
after.

Both 2.1 brains are available through Voice Live as managed models, with no Foundry

| surface | brain | `server_vad` | `semantic_vad` | `azure_semantic_vad_multilingual` |

| Voice Live | `gpt-realtime-2.1` | accepted | accepted | accepted |
| Voice Live | `gpt-realtime-2.1-mini` | accepted | accepted | accepted |

That matters because Azure's multilingual semantic detector was the one that eliminated

those arms existed and is superseded by the tier block above.

## What it would take on the Kataleptic side

*Read from `gateway/duguet-gateway.py` and `gateway/voicelive_engine.py`. Read-only — this
describes the change, it does not make it. Line references are approximate; the gateway has
moved since the earlier recon (it now carries a per-SKU `AZURE_REALTIME_RATE_TABLE`).*

Mostly small. One part is not, and it would fail silently if missed.

**1. Catalog entry** — a `MODELS` entry beside `kataleptic-realtime-hd`, with
`backend="voicelive"` and `backend_model="gpt-realtime-2.1-mini"`. Use an id that is *not*
a bare `gpt-realtime-*` name, e.g. `kataleptic-realtime-native`: `_native_realtime_model()`
routes on `backend == "azure-realtime"`, so a distinct id keeps the two engines from
fighting over it.

**2. Engine routing** — the dispatch hardcodes the tier id:

```python
elif _stripped_rt == "kataleptic-realtime-hd":
    engine = "voicelive"
```

That needs to become a `backend == "voicelive"` lookup, mirroring how
`_native_realtime_model()` already works for the native engine. Its docstring promises
"adding a new native SKU is a MODELS entry … no dispatch edit"; the voicelive side does not
yet keep that promise.

**3. Per-tier upstream model** — `VoiceLiveSession(model=VOICELIVE_MODEL)` reads a single
global env var, so every voicelive tier is the same brain. It needs the tier's
`backend_model`, the way the native path already passes a per-SKU deployment.

**4. Voice handling — the part that fails silently.** `map_voice()` coerces *every* OpenAI
voice name to an Azure neural voice unconditionally, and `initial_session_event()` injects
`DEFAULT_AZURE_VOICE` before any client event. Voice Live **accepts** an Azure neural voice
on a native-audio brain — verified: `gpt-realtime-2.1` echoes back
`en-US-AvaMultilingualNeural / azure-standard` without complaint.

So a tier wired up without touching this would **silently convert the native tier into an
Azure-TTS cascade** — the model's own prosody replaced by Azure synthesis, which is the
entire reason to want the tier — while looking like it works and still billing at native
rates. Both call sites need gating on the existing `is_native_audio(self.model)` helper,
which already returns `True` for anything starting with `gpt-realtime`.

**5. Detector default** — `_translate_td()` maps `semantic_vad` →
`azure_semantic_vad_multilingual` only when `not self.model.startswith("gpt-realtime")`.
This tier wants exactly that mapping *on* a gpt-realtime brain. Simplest is for the tier's
`initial_session_event()` to set `azure_semantic_vad_multilingual` directly, so the
behaviour does not depend on what the client happens to send — and given the injection race
below, a server-side default is more reliable than a client-side one anyway.

**6. Billing** — `is_native_audio("gpt-realtime-2.1-mini")` is already `True`, so the
audio-token meters are right. But `model_tier()` returns `"std"` for it because the
`"mini" in m` test precedes the `gpt-realtime` test, and whether Voice Live actually bills
a gpt-realtime-2.1-mini at Std rates needs checking against the price list. The native path
already solved this properly with a per-SKU rate table and a refuse-the-session guard when
an entry is missing; the voicelive path still infers rates from the model name. Worth
giving it the same treatment rather than trusting the heuristic — the failure mode is
underbilling a pricier SKU, silently.

**Not needed:** the dialect translation itself. `VoiceLiveSession` already speaks the flat
Voice Live shape and the GA↔flat translation is brain-agnostic; `_translate_transcription()`
already leaves the client's model alone for `gpt-realtime*`, so `whisper-1` passes through.
The measured arms in this report are exactly what that path would produce.

### Also worth fixing while in there

The **session-update injection race** documented above and in the merged report — the
gateway dials upstream lazily and its injected `session.update` sometimes lands after the
client's, dropping `semantic_vad`, the STT model, or the whole `turn_detection` block. It
cost 3 of ~57 gateway turns in this run's latency block (rejected as control divergences,
which is why the numbers are clean). Injecting before accepting the client socket, rather
than after, would remove a class of intermittent misconfiguration that no client can detect
without reading the echo back.

## An observation, not a result: the mini tier deflects

Counting replies where the agent says it cannot see or access the schedule, rather than
playing the receptionist:

| arm | deflecting replies |
|---|---:|
| `gw-21mini-semantic` | 6/20 |
| `gw-21-semantic` | 3/20 |
| `gw-21mini-server` | 2/20 |
| `gw-2-server`, `gw-21-server`, `gw-hd-server` | 0/20 |

> `gw-21mini-server`: *"Hi there! I can't see our live schedule from here, so I can't
> confirm a Thursday afternoon opening directly. Give us a quick call…"*
>
> `gw-21-server`: *"Let me take a moment to think through the schedule and see what's
> possible. We may have openings, so I'll need a time window…"*

**Treat this as a hypothesis, not a finding.** It is a crude regex over 20 replies per arm,
and it is confounded: the semantic-VAD arms hear the whole sentence while the server-VAD
arms hear only a fragment, so "which text the model saw" varies alongside the brain. It is
also part of why the mini tier is faster — a deflection is a shorter reply.

But it is the right question for the quality benchmark (task #14), and it bears directly on
whether 2.1-mini can be a default: a receptionist that tells callers to phone back is fast
and useless. **Do not adopt 2.1-mini on latency evidence alone.**

## Cost

**$7.36** across seven blocks (568 turns), well inside the $10 cap.

Cost per billed minute at Azure retail, no margin — the number that matters for a tier
decision:

> **The proposed tier's price is bounded, not verified.** Voice Live meters are named by
> service tier (Pro / Std / Lite), not by model — verified against
> `prices.azure.com` for swedencentral on 2026-08-03: Std LLM audio is $0.011 in /
> $0.022 out per 1K tokens, Pro is $0.032 / $0.064. **Which tier Azure bills
> `gpt-realtime-2.1-mini` at is not stated in the price list**, and this report's earlier
> $0.020 came from the harness's own heuristic (any model id containing "mini" → Std),
> not from a verified mapping.

| tier | $/min if **Std** | $/min if **Pro** |
|---|---:|---:|
| **proposed (gpt-realtime-2.1-mini via Voice Live)** | **$0.020** | **$0.062** |
| proposed with gpt-realtime-2.1 | $0.021 | $0.064 |
| current HD tier (gpt-4.1-mini, Std confirmed by its catalogue entry) | $0.020 | — |
| current gpt-realtime-2 tier (Foundry, native meters) | $0.068 | — |

**What the recommendation looks like each way:**

* **If Std** — the tier is a strict price match for HD: same $0.020/min, 357 ms faster,
  0/12 splits, native brain. A free upgrade for HD businesses.
* **If Pro** — it costs **~3.1× the HD tier** and roughly the same as the current
  gpt-realtime-2 tier. It would still be much faster than either (1528 ms p50 against
  1885 and 2266) with better turn-taking than gpt-realtime-2 — but for an HD business it
  becomes a *paid* upgrade, not a free one, and that changes who should be moved.

**Do not quote "matches HD on price" until this is settled.** Two ways to settle it: read
Microsoft's Voice Live pricing page for the model→tier mapping, or run a metered session
and read the actual meter from Azure Cost Management once it posts (8–24 h lag). The
gateway has the same exposure — `voicelive_engine.model_tier()` infers the tier from the
model name, with `"mini" in m` taking precedence, so a Pro-billed mini SKU would be
underbilled silently. The native path already solved this with a per-SKU rate table and a
refuse-on-missing guard; the Voice Live path should get the same.
