## Session logout failure security and Failed Logout

Two conclusions must remain separate. The current application does not silently discard the failure: Onboarding145 and Shell207 call the shared signOut and route to Auth, while App96–112 owns the pending/failure state. CompatibilitySessionCoordinator54–74 increments generation, sets pending and calls clearLocal synchronously before awaiting logout. App clearSession60–67 clears private identity/workspace state. Refresh37–51 refuses new loads while pending/unconfirmed and rejects older generations. Auth101–129 renders pending status or an accessible unconfirmed warning with explicit retry; its native controls and submit24 guard block authentication while unresolved. Onboarding marking itself inactive prevents stale page work after local clear; retaining an authenticated editing component is not a prerequisite for displaying the shared failure state.

However, the original's valid-cookie consequence is supported conditionally. Login/signup issue a Secure HttpOnly path-/ session cookie with a30-day maximum age (index339/431). Logout435–440 awaits deleteSession before deleteCookie. A transport failure before server handling, or a failing DELETE, can leave both session row and cookie. A response lost after deletion is ambiguous to the browser but need not leave a valid server session; distinguish those cases. getUserIdFromSession73–91 accepts a present, unexpired row. JavaScript cannot directly erase the HttpOnly cookie. The current coordinator and App warning exist only in memory: no storage restore occurs before App's initial refresh115–117. Reload/remount creates an idle coordinator and permits cookie-backed me/business/bootstrap loading again. Same-tab reload and a separate context that has access to that still-valid cookie therefore remain exposure risks. A wholly separate cookie jar is not asserted to inherit the session.

Qualified disposition: decline only the claimed silent/no-warning mechanism and the suggestion that merely awaiting navigation fixes revocation. Accept the conditional failed-revocation plus lost-on-reload latch risk. Prior source declines and green CI are not security clearance.

### Narrow feasible correction contract, not yet selected

A per-tab persistent sign-out intent is a feasible bounded mitigation for the specific lost-on-reload latch. Recommend sessionStorage, scoped explicitly to the same origin and tab, rather than silently promising a global logout or introducing cross-tab serialization. Store only a versioned non-secret intent marker: no identity, cookie, token, credentials or private workspace data. Record intent synchronously before local clear/request. Restore an outstanding intent before initial cookie-backed session loading; show the existing unconfirmed Auth/retry state and finish loading into the cleared UI, without an automatic logout request or automatic authenticated refresh. Retain the existing synchronous local clear, generation guards and pending/unconfirmed authentication gates. Keep the marker through rejection and pending navigation; clear it only after the current owned sign-out attempt confirms success. Old superseded completions must neither clear a newer intent nor unlock authentication. Explicit retry remains the action that attempts server revocation; no new timeout or automatic retry is proposed.

Storage read/write/remove failures need defined conservative behavior before preparation: always retain the memory latch/local clear and honest unconfirmed warning; never claim reload persistence if storage is unavailable. If removal fails after successful revocation, retaining a conservative retry gate is safer than silently manufacturing durable clearance. Initial storage failure must not crash the app or expose an authenticated snapshot under a claimed persistence guarantee. The contract must preserve ordinary successful sign-in and existing workspace snapshot publication when no outstanding intent exists.

This deliberately does NOT revoke the server row during network failure, clear a stolen/replayed cookie, protect direct API access, guarantee a new tab/browser/profile, survive cleared/unavailable storage, or provide universal browser restart persistence. SessionStorage is tab-scoped; choosing shared localStorage later would require a separately explicit cross-tab event and concurrent-intent/late-completion contract. A non-secret client flag is user/script-removable, not an authorization control. A same-tab mitigation alone must not be described as full security resolution.

Rejected shortcut: moving deleteCookie before a failed database delete can clear this browser's cookie when a response arrives, but leaves a live server token and loses the browser's handle for a subsequent deletion retry. A later no-cookie logout returns success without revoking that old row. This is not a substitute for confirmed revocation, and unconditional client-side success or merely awaiting navigation cannot make offline server deletion succeed. No server/schema/auth redesign is selected.

If the bounded persistence mitigation is selected after QA, future discriminating evidence should cover a failed logout followed by a new App/coordinator with the same tab storage (no authenticated load/publish), pending reload, explicit successful retry clearing the intent, repeated failure retention, stale completion versus newer intent, unavailable storage, and the ordinary no-marker login path. Browser evidence is needed for actual reload/storage/Auth wiring; source/unit reasoning alone is not that evidence. These are proposed behaviors, not prepared fixtures, commands or executed results. The separate valid-cookie/direct/new-context limits must remain visible even if all bounded cases pass.
