## Disposition

The schema claim is supported. Migration0008 constrains item.business_id and item.collection_id independently. The attachment table has two independent foreign keys. Neither proves equal workspace ownership. No later shipped migration adds the missing equality guards; 0013/0015 separately prohibit changing item/collection/assistant business ownership.

No current untrusted HTTP producer of a mismatched relationship was established. Existing call knowledge explicitly joins all three business identities and excludes corrupt combinations. Therefore do not describe the missing schema equality as a demonstrated remote tenant attack or live-call disclosure. Do not claim all reads are corruption-safe: Studio collection item pagination and attached-assistant metadata reads trust stored relationships and could disclose another business's content/metadata if privileged SQL, an external import or earlier corruption first installs a mismatched row. This conditional consequence is source-supported, not newly executed evidence.

Recommend selecting a narrow additive database invariant as defense in depth. Its upgrade/refusal semantics must be selected before source preparation. No shipped migration rewrite, table rebuild or automatic historical reconciliation is needed for the proposed scope.

## Proposed additive migration policy, not selected

1. Integration reserves the next migration number only after contract agreement. Keep0008/0013/0015 and every other applied migration byte-identical. Prefer four ownership triggers over rebuilding tables/composite FKs: item BEFORE INSERT and BEFORE UPDATE OF business_id,collection_id require a matching collection; attachment BEFORE INSERT and BEFORE UPDATE OF assistant_id,collection_id require existing parents with equal business. Missing parents are refused too. Existing parent immutability and ordinary FK checks remain the complementary guarantees; this does not defend against an administrator disabling/dropping constraints.
2. Before any DDL, inspect the two proposed invariants with NOT EXISTS membership checks so missing parents do not disappear from an inner join. Abort the migration on any inconsistent item or attachment. Execute precondition and guard creation in one atomic migration transaction; prove late failure rollback before release. Existing0016/0018's conditional failure pattern is precedent, not authority to rewrite those files.
3. No backfill is required for consistent data. Do not infer whether a mismatched item's business or collection is authoritative. On refusal, keep all rows, content, IDs, source refs, timestamps, attachments and counters unchanged; provide counts/read-only diagnostics and require explicit operator reconciliation outside this migration. Do not delete, reassign, detach, reset budgets or silently skip a failed migration.
4. Triggers perform validation only, no successful-write DML. An invalid statement must leave all rows and counters unchanged even if budget triggers run first; RAISE(ABORT) and enclosing batch rollback must be demonstrated without depending on undocumented trigger ordering. OR IGNORE attachment inserts must still refuse mismatches. Valid writes retain the same charges; attachment writes do not gain a quota charge.
5. Trigger UPDATE scope excludes source_call_id/source_turn_id-only SET NULL cleanup; preserve current cascade deletes and all existing source-reference behavior. Preserve CAS zero-write conflicts, atomic legacy-source/mirror/snapshot batch behavior, provider predicates, Unicode checks and CREATE attachment changes() ordering. No new source-ref constraint, enum policy, timestamp/version or broad writer refactor.
6. Migration-before-upload / failed-upload contract: valid old/current issuers continue under installed guards; rollback to an older Worker does not authorize dropping guards. Pre0008 Workers edit legacy data; current repair emits same-tenant rows. Invalid privileged imports now fail. If the migration itself fails, do not publish the dependent release or mark it applied; keep prior schema/data and explicitly reconcile. Emergency DB restore is an operator decision, not an automatic downgrade/deletion step.
7. Read filtering is a separate possible selection: add matching-business predicates to the affected Studio item/attachment joins if protecting still-corrupt pre-upgrade databases is desired. That changes corrupted-data presentation and should not be silently bundled with this migration. The proposed atomic refusal means migration alone does not sanitize already-served corrupt data. No remote corruption inventory or actual production-state claim has been made.

- Clean migration-through-current upgrade: identity/content/count/source-ref/counter preservation; valid API item creation/move, attachment, legacy JSON sync and missing-default foundation repair still work. Existing read-filter corruption fixture remains attributed to pre-guard schema; do not weaken it merely to seed corruption after guards.
