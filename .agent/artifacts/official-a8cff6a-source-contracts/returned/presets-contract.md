## Delete Race: supported at the recovery boundary

The stated race is concrete once missing-default recovery is needed. Start with a surviving nondefault canonical-named row and no default in that workspace. D reads that row as nondefault. R runs foundation: the insert is skipped because the name exists; promotion sets is_default1 and repair commits its attachment/projection. D then executes its unconditional DELETE and removes the newly protected default plus cascading items/attachments.

This starting state is explicitly handled by current foundation and by the existing test `repairs an existing named default without attempting a quota-charged duplicate insert` (`test/studio-api.test.ts:2052`), which seeds it by direct SQL demotion. No ordinary current UI/HTTP producer that clears the default flag or deletes a still-default collection was established. Normal onboarding/migration creates a default; current collection endpoints do not demote it. Therefore describe this as a recovery-state safety gap, not a demonstrated routine current-UI exploit. A concurrent rename alone does not promote a collection while another default exists.

Unlike an explicit pause command, deletion already promises “The default collection cannot be deleted” and evaluates a mutable protection predicate. Propose preserving that predicate at the delete linearization point: retain ownership404 and known-default409 prechecks, then DELETE matching id/business with `is_default=0`, returning the actual deleted id; absence returns409. This also changes a concurrent disappearance after the initial read from acknowledged success to conflict, which must be explicit in selection. Prefer RETURNING identity over numeric affected-row assumptions because cascades can contribute to metadata changes.

No full collection/content CAS is proposed: deletion still intentionally removes the current contents of a nondefault target. No schema, default-selection redesign, repair ordering, trigger or automatic recovery change. The role predicate prevents all cascades when promotion wins. Ordinary allowed deletion still cascades, consumes no collection-write unit and refunds no prior quota.0013 collection UPDATE budgets do not include is_default/time, so promotion itself is uncharged; its knowledge reprojecting may charge item writes. Retain the repair's existing quota and whole-batch rollback boundaries.

## Create Race: duplicate persistence excluded; wrong conflict response supported

On a reconciled workspace with spare quota/storage, two POSTs with the same trimmed name can both observe no duplicate. A commits its INSERT. B's unconditional INSERT meets the `(business_id,name)` UNIQUE constraint; the index error mapper has no classification for it and returns generic500. The failed statement/batch rolls back its trigger counter effects; only A's collection and accepted charge remain. This is not duplicate collection persistence or a stored quota bypass. If a budget trigger refuses first at a boundary, the existing response can instead be storage409/daily429; generic500 is not universal.

Minimal proposal: retain the fast duplicate precheck, but make the requested INSERT SELECT conditional on no same-business/same-normalized-name row at execution time, still RETURNING the created row in the same one-statement batch. No returned row means duplicate409 using the existing duplicate response. A zero-input INSERT SELECT does not attempt a row and must not charge an INSERT trigger. Do not use broad `INSERT OR IGNORE` or catch every constraint as duplicate: those can mask unrelated failures and, depending on conflict handling, retain unwanted BEFORE-trigger side effects.

Preserve database UNIQUE as authority, existing trimmed-name/description/defaults,201 actual INSERT response, workspace ownership/foundation order, and unrelated FK/storage/quota/error propagation. Duplicate-at-write409 takes precedence over quota only for the skipped row; a unique requested row still encounters all existing limits. A stable identical retry remains409 without a second requested row/charge. Transport loss is not solved by this proposal.

The inventory also shows collection PUT can lose an analogous name race: its target's captured name/description can remain unchanged while another collection claims its desired name, leading to UNIQUE refusal after its precheck. It can also be the winning writer against POST. This is a concrete adjacent residual contract gap, not permission to expand the selected POST/DELETE correction. Integration should explicitly decide whether to include PUT uniqueness separately; do not claim a POST-only correction closes every collection-name conflict. Existing PUT stale-merge CAS must be preserved.

## Invalid Input: premise disproved for submitted JSON fields

`src/index.ts:644` invokes the imported runtime `readWorkspaceBody` before deriving effective values or running compatibility/essentials checks. `src/request-validation.ts` includes agent_name, persona and language in TEXT_FIELDS; every supplied nonstring, including number/object/boolean/null/array, throws HTTPException400 with a field-text error. The index error handler returns that response unchanged. The three reported payloads cannot reach their `.trim()` calls through this handler. No redundant route validation patch is proposed.

Precedence: authentication401 and global body-size413 precede handler work; missing/foreign business or missing canonical assistant404 precede body parsing; malformed/nonobject JSON and supplied nonstrings400 precede key handling, provider compatibility, workspace completion and effective-string checks. Omission is not null: omitted properties retain the captured current strings; supplied null is400. Empty/whitespace strings are valid types but still encounter the existing required-field400, subject to earlier provider checks and the existing draft/incomplete-workspace409. Do not reorder those branches or convert omission into required submission. The route performs read-only ownership/configuration reads before validation; these invalid submitted fields produce no requested DML, counter, provider, legacy mirror or snapshot writes.

The claim concerns untrusted submitted types, not arbitrary privileged corruption of persisted rows or a general schema validator. No broader enum normalization, field coercion or validation-order redesign is justified. Preserve all current provider/text/CAS predicates and uninterrupted changes-gated writes.
