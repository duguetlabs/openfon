**Session revocation / Logout Failure — qualified decline of the silent-failure premise.** Onboarding calls the shared App signOut before navigating. CompatibilitySessionCoordinator invalidates stale loads and clears local private data before the request. Rejection sets its unconfirmed state and invokes App's failed callback before reaching the local catch. Auth then shows an alert: “This screen was cleared, but server sign-out was not confirmed. Retry sign-out before leaving this device.” It offers Retry sign-out, blocks login/signup both visually and synchronously, and suppresses background refresh until confirmation. The local catch consumes an already-presented error; it does not hide the only notification or claim server revocation succeeded. Backend deletion precedes cookie deletion and200. Relevant exact sources: [App](https://github.com/duguetlabs/openfon/blob/aa7467566662a4c43b54563226e78abeb575dc2d/web/src/App.tsx#L96), [coordinator](https://github.com/duguetlabs/openfon/blob/aa7467566662a4c43b54563226e78abeb575dc2d/web/src/session-load.ts#L54), [Auth alert/retry](https://github.com/duguetlabs/openfon/blob/aa7467566662a4c43b54563226e78abeb575dc2d/web/src/pages/Auth.tsx#L101).

The residual risk is real: failed server deletion may leave a valid HttpOnly cookie; the latch/warning are memory-only, so reload or a new tab can authenticate again. A lost response may also leave a successfully deleted session. This is explicitly unconfirmed logout, not a guarantee of revocation while the server is unavailable. Users must confirm retry before leaving a shared device. No durable cross-tab/reload lockout or offline revocation is claimed or newly selected. Merely awaiting the rejected request while retaining the private screen would not fix server unavailability. Existing coordinator tests cover warning/retry/auth and refresh guards; no new Onboarding failed-logout browser reproduction is claimed.
