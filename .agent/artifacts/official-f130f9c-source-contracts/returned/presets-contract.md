## Narrow proposal for integration selection, not prepared

Recommended minimum contract: a reconciliation must not apply an obsolete source/marker/default decision or silently overwrite affected rows changed after the decision's recorded observation. Refuse that invocation with an explicit conflict; do not automatically retry its destructive plan. Preserve genuine fresh legacy replacement and projection-equivalent no-op/cleanup behavior. This is read-to-write protection, not permanent typed ownership or UI-draft freshness before the handler reads.

A possible implementation would need all of the following, not just a predicate added to DELETE:

- Establish coherent expected source JSON and knowledge marker presence/values and collection choice for the plan. For repair, the source driving projection must actually match the workspace's current source; merely reading/pinning a new source while still using the old passed object is insufficient. For business PUT, distinguish the expected OLD source from requested NEW values. Guard both source columns because the current leading UPDATE and final marker also write the omitted sibling. Do not expand into unrelated full business/assistant CAS by assumption.
- Record the entire affected prefix membership and relevant deleted row state, including absence/deletion, collection move, kind/status/content and any preserved metadata policy. Checking only rows that remain or a count cannot detect additions, deletion/recreation or equal-byte edits. Item edits leave source/marker unchanged, so source pins alone cannot protect this interval. Timestamp equality is not a revision, and ABA/exact-identical replacement limits require explicit disclosure.
- Make a failed expectation refuse the WHOLE sync batch, including its leading source/repair writes, INSERTs and final marker, before an externally acknowledged success. Optional zero-row DELETEs and empty source arrays are legitimate, so changes()>0 chaining per DELETE is invalid. A same-value final marker is not proof that a guard accepted. No exact SQL mechanism/marker/error mapping has been selected or tested here.
- Preserve new-workspace/missing-default batch ordering, no known-quota-failure writes, exact single-row quota charges, unchanged families/random-ID rows, tenant guards, provider/assistant foundation pins and all previously closed RETURNING behavior. Limit rollback promises to the guarded batch; earlier foundation repair remains committed. Decide how a conflict is surfaced through GET/public/setup callers instead of allowing an unclassified generic500 or unsafe automatic destructive retry.

Residual: if source and marker still legitimately differ after a refusal, a later FRESH repair may intentionally replace a typed row already present at its observation. The proposed interval guard cannot promise that an edit survives all later legacy source changes. Permanent typed precedence would require a distinct ownership/merge/conflict-resolution policy (including draft/deletion tombstones), not a snapshot-only fix. Missing-default repair can likewise intentionally reconstruct original source. The current business PUT's unrelated omitted-field full-row merge is outside this knowledge-only proposal; protecting source columns is not blanket lost-update clearance for business fields.
